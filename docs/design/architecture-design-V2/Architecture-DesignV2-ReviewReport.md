## 執行摘要（Executive Summary）

本報告針對《Claude All-in-One V2 架構設計報告》（以下簡稱 V2 設計）進行嚴格的 AI SDLC 合理性審視。

**整體評估結論：高度合理、工程嚴密，且具備頂級的 AI 治理（Governance）思維。**

V2 架構擺脫了當前業界常見的「盲目多代理（Multi-agent）狂熱」，選擇了 **「程式優先（Program First）、脈絡分離、以 Main 為核心、證據驅動」** 的務實路線。該設計精準擊中了 AI 代理在實際軟體工程中最致命的幾個痛點：**脈絡污染（Context Contamination）、語言幻覺（Hallucination）、權限膨脹（Privilege Escalation）與無法追溯（Lack of Auditability）**。

雖然架構邏輯極為嚴謹，但在**實作複雜度**與**開發流暢度（Developer Experience）**之間仍存在一定的工程張力。本報告將詳細剖析其優勢、潛在隱憂，並提出具體的落地執行建議。

## 一、 AI SDLC 架構合理性分析

V2 架構在 AI SDLC 的維度上，展現了極高的工程成熟度，其合理性體現在以下四個核心柱石：

```
                    +-------------------------------------------------+
                    |           Main Session (唯一整合決策者)           |
                    +-----------------------+-------------------------+
                                            |
         +----------------------------------+----------------------------------+
         |                                  |                                  |
         v                                  v                                  v
+------------------+              +------------------+              +------------------+
|     Program      |              |    Main Skill    |              |  Worker Agent    |
| (確定性程式檢查)  |              | (載入程序親自執行) |              | (強隔離/有界委派) |
+--------+---------+              +--------+---------+              +--------+---------+
         |                                  |                                  |
         +----------------------------------+----------------------------------+
                                            |
                                            v
                                +-----------------------+
                                |  Evidence Manifest    |
                                | (原始日誌與 SHA-256)  |
                                +-----------------------+
```

### 1. 貫徹「確定性程式（Program）優先」原則
在 AI SDLC 中，將確定性邏輯（如 Git 狀態檢查、語法檢查、單元測試、環狀依賴判定）交由 AI 模型處理，既浪費成本又不可靠。V2 設計將 **Program** 置於排程體系的最優先順序（Priority 1），徹底限制了 LLM 推理的邊界，確保基礎設施的確定性。

### 2. 「技能（Skill）」與「執行位置（Actor/Runtime）」的徹底解耦
過往的多代理設計常陷入「一項專業能力 = 一個獨立 Agent」的誤區，導致對話開銷與 Token 成本呈指數暴增。V2 將 Skill 定義為「可按需載入的專業程序」，預設由 Main 載入執行；只有在需要隔離大量輸出或平行探索時，才指派受限子代理（Worker）。這極大地優化了上下文視窗（Context Window）的利用效率。

### 3. 雙向交接與結構化結果契約（Context Handoff Contract）
AI 代理間的資訊傳遞是「幻覺與資訊丟失」的高發區。V2 定義了嚴格的 `handoff.json` 與 `result.json`，強制約束輸入來源版本、角色邊界、未解問題（`open_questions`）與原始位元組指紋（`SHA-256`）。這打破了「代理自稱完成即等於完成」的黑盒子。

### 4. 嚴格的防護與單一事實來源（Single Source of Truth）
V2 在安全設計上採取了零信任（Zero Trust）態度：
- **禁止自動升權**：模型的推論能力提升（如切換至 `think` 層級）不帶來任何額外的檔案或 API 權限。
- **權威分離**：決策原文只在 `decisions/`，階段狀態由 `state.json` 權威持有，禁止摘要成為第二個可編輯的權威來源。

## 二、 深度風險審視與潛在隱憂

儘管設計原則相當優異，若從實務開發的角度切入，仍有以下三個風險點需要高度關注：

### Risk 1: 「行政負擔（Over-Engineering）」破壞開發流暢度
* **問題剖析**：V2 規範了大量的 JSON Schema、帳本型態（`stage_attempt` vs `runtime_event`）、交易復原機制（Transactions）與鎖檔（Writer Lock）。
* **AI SDLC 衝擊**：若 Runtime 自身的腳本寫得不夠自動化或執行過慢，可能出現 **「AI 產生程式碼 1 分鐘，Runtime 處理狀態轉換與驗證契約花了 3 分鐘」** 的窘境，損害單一開發者的協作體驗。

### Risk 2: 平台實際隔離行為的不確定性
* **問題剖析**：報告 §7.4 要求 Runtime 必須檢查平台回報的 `actual_context_mode`（如 `fresh` 或 `fork`）。
* **AI SDLC 衝擊**：目前的商業 LLM CLI 或 API（如 Claude Code、Codex）底層運作機制經常更迭，未必能穩定且透明地提供真正的環境隔離證明。若平台底層行為不符預期，可能導致獨立審查（Independent Review）無意間遭污染。

### Risk 3: Eval 評測集的獲取成本
* **問題剖析**：設計強調透過比較實驗（Eval，24 題基準）來判斷委派策略（Delegation Policy）是否划算。
* **AI SDLC 衝擊**：在專案開發初期，構建 24 題具代表性且可重現的 AI 測試集需要耗費大量精力。若為了追求「量化指標」而延遲了核心功能的替換，可能會陷入過度優化的泥淖。

## 三、 對 AI SDLC 落地執行的關鍵建議

為了讓 V2 架構順利落地，並發揮其最大價值，提出以下四點針對性的執行建議：

### 建議一：嚴格實施「預設全由 Main 執行」的保守策略
在 **U0 至 U5** 的重建過程中，建議不要急於開啟子代理（Subagent）的並行運作。
* **做法**：優先將「Main 載入 Skill 執行 + 確定性 Program 驗證」的單路徑做到極致。
* **價值**：事實證明，約 80% 的日常 SDLC 任務在 Main 內完成即有最高效益；把 U6 的多子代理當成「高階擴充元件」，而非「上線前提」。

### 建議二：基礎設施輕量化，由工具封裝契約細節
必須保證開發者（Human-in-the-loop）不需要手動干預任何 `.cai/track/` 下的 JSON 檔案。
* **做法**：將 `task_graph.py`、`ledger.py` 與 `evidence.py` 的操作完全封裝至低延遲的 Python CLI 中。
* **驗收**：任何狀態轉移與帳本追加，寫入時間應控制在 **100ms** 以內，避免影響對話體驗。

### 建議三：建立「隔離失效時的自動降級機制（Fallback）」
針對平台適配的不確定性：
* **做法**：當 Runtime 無法精確驗證平台是否確實建立了 `fresh` 隔離脈絡時，系統應**自動降級為由 Main 序列執行**，並在帳本中標記 `CONTEXT_MODE_UNVERIFIED`。
* **原則**：寧可犧牲並行速度，也絕對不冒「假獨立審查」的安全風險。

### 建議四：貫徹一次性替換（U7 Cut-over），避免兩套系統並存
同意並支持設計報告中的 **R6 / AC6** 決定。
* **做法**：不要試圖在新系統中相容 V1 的舊狀態、Markdown 檔案或歷史帳本。V2 Merged 後直接以全新的 Track 開始。
* **價值**：切斷歷史包袱是確保新架構「單一事實來源」與「不可變帳本」能純粹運作的唯一途徑。
